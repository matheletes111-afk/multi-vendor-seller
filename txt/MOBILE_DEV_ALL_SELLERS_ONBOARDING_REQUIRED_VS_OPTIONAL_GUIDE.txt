CORE RULES ENFORCED BY THE WEB PLATFORM:
- UI Astrixes & Blockers: Any field marked with an asterisk (*) on the web 
  is strictly validated by the client-side `handleNext` function before 
  allowing the seller to advance to the next step.
- Step Numbering Compatibility:
  - Mobile Apps can submit using 1-based `mobileStep` (1 to 5) OR 
    database-based `step` (2 to 6).
  - The backend also uses smart field signature detection as a fallback.
- Status Life Cycle:
  [Registration] -> [Onboarding Steps 1-5] -> [Submitted: PENDING] -> [Admin Review]
  - If approved: `status: "APPROVED"` -> full dashboard unlocked.
  - If correction needed: `status: "CORRECTION_NEEDED"` -> seller sees 
    `adminFeedback` and can re-submit the specific step/files.

3. FILE UPLOAD TECHNICAL SPECIFICATIONS & SIZE CONSTRAINTS
================================================================================

3.1. ACCEPTED FORMATS & MIME TYPES
--------------------------------------------------------------------------------
1. IMAGE-ONLY FIELDS (Must be images, PDF upload will be rejected):
   - Profile Picture (`profileImage`)
   - Selfie Verification with ID (`selfie`)
   - Storefront / Restaurant / Hotel Logo (`logo` / `storeLogo`)
   - Storefront / Restaurant / Hotel Banner (`banner` / `storeBanner`)
   - Main Cuisine / Property Photo (`mainPhoto`)
   Allowed Extensions: .jpg, .jpeg, .png, .webp, .heic, .heif, .avif, .bmp
   Allowed Mime Types: image/jpeg, image/png, image/webp, image/heic, image/avif

2. DOCUMENT FIELDS (Accepts BOTH PDF and Images):
   - Business Registration Certificate (`busRegCert`)
   - GST / TIN Certificate (`gstTinCert`)
   - City Council Certificate (`cityCouncilCert`)
   - Proof of Business Address (`addressProof`)
   - ID Front & ID Back (`idFront`, `idBack`)
   - Food Hygiene License (`foodLicense`)
   - Bank Passbook / Cheque Copy (`bankPassbook` / `passbook`)
   - Bank Verification Letter (`bankLetter`)
   - Rider Driving License (`drivingLicenseDoc`)
   - Rider National ID Card (`nationalIdDoc`)
   - Rider Vehicle Insurance (`vehicleInsuranceDoc`)
   Allowed Extensions: .pdf, .jpg, .jpeg, .png, .webp

3. FORBIDDEN FORMATS (Server immediately responds with 400 Bad Request):
   - Word Documents: .doc, .docx
   - Excel Spreadsheets: .xls, .xlsx, .csv
   - SVGs: .svg (strictly blocked due to XSS vulnerability)
   - Executables & Archives: .exe, .bat, .zip, .rar, .7z

3.2. FILE SIZE LIMITS & COMPRESSION GUIDELINES
--------------------------------------------------------------------------------
- Web Client Limit: Web onboarding client checks `file.size <= 2.5 MB`.
- Server Limit: API endpoint allows up to `4.5 MB` before rejection.
- Mobile Best Practice:
  - Compress camera captures on device to JPEG/WebP quality 80% (target 300KB - 800KB).
  - Recommended dimensions:
    - Profile & Logos: 500x500 to 800x800 square (1:1 aspect ratio).
    - ID Cards: 16:10 or 3:2 aspect ratio.
    - Banners: 16:9 widescreen ratio.
    - Main Property Photos: 4:3 or 16:9 ratio.

6. SERVICE PROVIDER ONBOARDING SPECIFICATION (/service-seller)
================================================================================
Base Endpoints:
  - GET  /mobileapi/service-seller/onboarding
  - POST /mobileapi/service-seller/onboarding
  - GET  /mobileapi/service-seller/categories (For Service Categories)

Service Seller follows the exact same 5-step flow and validations as Product Seller,
with the following domain adjustments:

1. Step 1 (DB Step 2):
   - Field `busRegCert`: Labeled on web UI as "Business Registration Certificate / Trade License *".
   - Field `profileImage`: Labeled on web UI as "Provider Profile Picture *".
   - `street`, `city`, `district` (Area *), `haveGst`, `taxIdNumber` are all REQUIRED.
   - `postalCode` is OPTIONAL (hidden with `display: none`).

2. Step 2 (DB Step 3):
   - `nationIdentityNumber`: REQUIRED ("National Identity Number (NIN) *").
   - `idType`, `idNumber`, `idFront`, `idBack` (unless passport), `selfie` are REQUIRED.

3. Step 3 (DB Step 4):
   - Identical Bank vs Mobile Money payout rules.

4. Step 4 (DB Step 5):
   - UI Header: "Service Profile & Category Setup".
   - `selectedServiceCategories` or `categoryIds`: REQUIRED (At least 1 service category chosen).
   - `storeLogo`: REQUIRED (Service provider logo / badge).
   - `storeBanner`: OPTIONAL.

5. Step 5 (DB Step 6):
   - All 4 legal checkboxes (`agreedToTerms`, `agreedToPrivacy`, `agreedToReturnPolicy`, 
     `agreedToCommission`) + `hearAboutUs` are REQUIRED.

10. UNIFIED PAYMENT & PAYOUT SETTLEMENT RULES (BANK VS MOBILE MONEY)
================================================================================
All sellers and riders share the exact same payout normalization engine
(`validateAndFormatPaymentDetails`). The mobile app UI MUST dynamically switch
visible fields based on the selected `paymentOption`:

OPTION A: "Orange Money" OR "AfriMoney"
--------------------------------------------------------------------------------
1. `mobileNumber`       --> [MANDATORY]: Valid mobile phone number.
2. `agentNumber`        --> [OPTIONAL]: Agent code for cash pickups.
3. Bank Fields          --> [DO NOT SEND / NULL]: All bank fields are automatically 
                            cleared to null by the server.
4. Passbook / Letter    --> [NOT REQUIRED]: Document proofs are omitted.

OPTION B: "Bank"
--------------------------------------------------------------------------------
1. `bankName`           --> [MANDATORY]: Commercial bank name.
2. `accountHolderName`  --> [MANDATORY]: Legal account holder name.
3. `accountNumber`      --> [MANDATORY]: Account number.
4. `bbanNumber`         --> [MANDATORY]: Basic Bank Account Number.
5. `branchName`         --> [MANDATORY]: Branch name or IFSC routing code.
6. `bankAddress`        --> [MANDATORY]: Street address of branch.
7. `passbook`           --> [OPTIONAL]: Passbook or cancelled cheque image.
8. `bankLetter`         --> [OPTIONAL]: Bank verification letter.
9. Mobile Money Fields  --> [DO NOT SEND / NULL]: Mobile numbers are ignored.

12. MOBILE API INTEGRATION GUIDELINES & ERROR HANDLING
================================================================================

12.1. AUTHENTICATION HEADER
--------------------------------------------------------------------------------
Every request must supply the Bearer JWT token:
  Header: Authorization: Bearer <mobile_access_token>

12.2. STEP NUMBERING DISPATCH
--------------------------------------------------------------------------------
You may pass either:
- `mobileStep`: 1, 2, 3, 4, or 5
- OR `step`: 2, 3, 4, 5, or 6
- OR pass `section`: "business", "kyc", "bank", "store" / "outlet" / "property", "agreement"
The backend automatically resolves the correct step.

12.3. ADMIN CORRECTION WORKFLOW (CORRECTION_NEEDED)
--------------------------------------------------------------------------------
If an admin reviews an onboarding application and notices an issue (e.g., blurry 
ID, invalid tax certificate), the seller's `status` becomes `CORRECTION_NEEDED` 
with actionable notes in `adminFeedback`:
- The mobile app should check `status` and `adminFeedback` on `GET /onboarding`.
- If `status == "CORRECTION_NEEDED"`, present the feedback prominently on screen 
  and allow the seller to update the required step/file without having to re-enter 
  all previous data.

12.4. ERROR HANDLING FORMAT (400 Bad Request)
--------------------------------------------------------------------------------
```json
{
  "success": false,
  "error": "Cannot complete onboarding: Missing required documents: Business Registration Certificate, Selfie with ID"
}
```

12.5. SUCCESS ONBOARDING COMPLETION RESPONSE (200 OK)
--------------------------------------------------------------------------------
```json
{
  "success": true,
  "message": "Registration completed successfully",
  "data": {
    "nextStep": null,
    "onboardingCompleted": true,
    "status": "PENDING"
  }
}
```
