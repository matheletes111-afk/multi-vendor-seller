1. EXECUTIVE SUMMARY & FINANCIAL LEDGER ARCHITECTURE
--------------------------------------------------------------------------------
All 4 Seller Panels (Product, Service, Hotel, and Restaurant) operate on a
unified, transparent financial ledger and settlement lifecycle:

A. SETTLEMENT STATUS LIFECYCLE (`settlementStatus`):
  1. "PENDING"                 — Order/booking placed with COD (not yet fulfilled)
                                 or unverified AfriMoney.
  2. "ESCROW_HELD"             — Customer paid online via AfriMoney (`COMPLETED`);
                                 platform holds funds in escrow until fulfillment.
  3. "YET_TO_PAY"              — Order/booking fulfilled (`DELIVERED` / `CONFIRMED`)
                                 where the platform collected the funds (AfriMoney
                                 prepaid OR platform rider collected COD for a
                                 product order). Seller's `netBalance` is credited
                                 and the platform owes this payout to the seller.
  4. "COD_COLLECTED_BY_SELLER" — Fulfilled via Cash on Delivery where the seller
                                 collected cash directly from the customer:
                                   * Hotel "Pay at Hotel" (`COD`)
                                   * Restaurant `COD` order
                                   * Service `COD` appointment
                                   * Product Self-Delivery `COD` order
                                 Because the seller already has the cash in hand,
                                 platform payout liability is 0 (`netBalance` is
                                 NOT incremented).
  5. "PAID_OUT"                — Admin has disbursed the `YET_TO_PAY` balance to
                                 the seller's Bank / AfriMoney / Orange Money
                                 account and recorded the Transaction Reference ID.
  6. "CANCELLED"               — Order/booking was cancelled.

B. GROSS SUBTOTAL COMMISSION BASE RULE:
  * Platform commission (`commissionAmount`) and Seller Net Payout (`sellerNetPayout`)
    are ALWAYS calculated on the seller's gross item/room/food `subtotal` BEFORE
    any platform-wide promotional coupon discount.
  * Platform coupon discounts are absorbed by the platform, never deducted from
    the seller's net earnings.

--------------------------------------------------------------------------------
A1. PRODUCT SELLER ORDERS LIST, DETAIL & STATUS UPDATE (WITH SETTLEMENT BREAKUP)
--------------------------------------------------------------------------------
Web List:        GET   /api/product-seller/orders
Mobile List:     GET   /mobileapi/product-seller/orders
Web Detail/Upd:  GET & PATCH /api/product-seller/orders/[id]
Mobile Det/Upd:  GET & PATCH /mobileapi/product-seller/orders/[id]
Auth:            Session Cookie (Web) | Bearer Token (Mobile - SELLER_PRODUCT)

Fulfillment & Settlement Trigger (`applySellerCreditForOrderLineDelivered`):
  * When an order line reaches `DELIVERED` (either via Rider OTP delivery in
    `/api/riderapp/orders/[id]/status` OR via Seller Self-Delivery OTP in
    `PATCH /api/product-seller/orders/[id]`):
    - If `paymentMethod === "AFRIMONEY"` OR Platform Rider delivered a `COD` order:
        * `settlementStatus` becomes `"YET_TO_PAY"`.
        * `seller.netBalance` is incremented by `lineInclGst - commissionAmount`
          (+ `shippingAmount` only if `isSelfDelivery === true` and `AFRIMONEY`).
        * `SellerBalanceTransaction` (`kind: "CREDIT"`, `reason: "ORDER_LINE_DELIVERED"`) is created.
    - If `paymentMethod === "COD"` AND `isSelfDelivery === true`:
        * Seller collected the cash directly from the customer.
        * `settlementStatus` becomes `"COD_COLLECTED_BY_SELLER"`.
        * `seller.netBalance` is NOT incremented (0 platform payout liability).

Mobile Det/Upd:  GET & PATCH /mobileapi/service-seller/orders/[id]
Auth:            Session Cookie (Web) | Bearer Token (Mobile - SELLER_SERVICE)

Fulfillment Behavior when Service Seller marks status = "DELIVERED":
  * If `paymentMethod === "AFRIMONEY"`:
      - `settlementStatus` becomes `"YET_TO_PAY"`.
      - `seller.netBalance` is incremented by `lineInclGst - commissionAmount`.
      - `SellerBalanceTransaction` (`CREDIT`) is created.
  * If `paymentMethod === "COD"`:
      - Service provider collected cash directly from customer at appointment.
      - `settlementStatus` becomes `"COD_COLLECTED_BY_SELLER"`.
      - `seller.netBalance` is NOT incremented (0 platform payout liability).
  * When all items in the parent Order reach `DELIVERED`, parent `Order.status`
    becomes `"DELIVERED"` and `Order.paymentStatus` becomes `"COMPLETED"`.

          * `restaurantSeller.netBalance` is NOT incremented (cash collected directly).

SECTION E: ADMIN CENTRAL PAYOUTS & DISBURSEMENT ENGINE
================================================================================

1. GET /api/admin/payouts
   Returns:
     * `summary`: `totalYetToPay`, `totalPendingRequested`, `pendingCount`,
       `totalDisbursed`, `disbursedCount`, `totalYetToPaySellersCount`.
     * `pendingRequests`: All `PENDING` payout requests across `PRODUCT`,
       `SERVICE`, `HOTEL`, `RESTAURANT`, and `RIDER`.
     * `yetToPaySellers`: All vendors/riders with `netBalance > 0`.
     * `disbursedHistory`: Historical `DISBURSED` payout requests.

2. POST /api/admin/payouts/disburse
   Request Payload:
   {
     "payoutRequestId": "cuid_req_1",       // Optional (if disbursing from Pending Requests tab)
     "sellerSector": "PRODUCT",             // "PRODUCT" | "SERVICE" | "HOTEL" | "RESTAURANT" | "RIDER"
     "sellerId": "cuid_seller_1",
     "amount": 450.00,
     "payoutMethod": "AfriMoney",           // "AfriMoney" | "Orange Money" | "Bank Transfer"
     "payoutAccountSnapshot": "Method: AfriMoney • Mobile: 077123456",
     "payoutReference": "AFRI-TXN-889900",  // Mandatory Transaction ID / Bank Ref
     "adminNote": "Settled weekly payout",  // Optional
     "orderId": null,                       // Optional (if disbursing specific order from modal)
     "orderItemId": null,                   // Optional
     "bookingId": null,                     // Optional
     "foodOrderId": null                    // Optional
   }

   Atomic Transaction Behavior:
     * Verifies `currentBalance >= amount` and decrements `netBalance`.
     * Creates a `DEBIT` balance transaction (`reason: "PAYOUT_DISBURSED"`) with
       full reference and method note.
     * Marks all corresponding `YET_TO_PAY` order items / hotel bookings / food
       orders / rider assignments as `PAID_OUT` with `payoutDisbursedAt`,
       `payoutReference`, `payoutMethod`, `payoutAccountSnapshot`, and `payoutNote`.
     * Updates the `SellerPayoutRequest` (or any existing `PENDING` request for
       that seller) to `status: "DISBURSED"`.
