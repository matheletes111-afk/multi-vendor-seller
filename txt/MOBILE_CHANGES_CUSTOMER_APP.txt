1. EXECUTIVE SUMMARY & ARCHITECTURAL SHIFT
--------------------------------------------------------------------------------
The backend authentication, user registration, and notification engine has
transitioned to a Phone-First architecture:
  * Phone is strictly MANDATORY on registration.
  * Email is OPTIONAL on registration.
  * Primary OTP verification occurs via SMS to the customer's phone number.
  * Dual Credential Login: Customers can log in using either their Mobile Number
    or their Email Address with their password.
  * JWT Token Claims: Mobile tokens now carry "phone: user.phone".
  * Settings & Profile: Customers can add, update, or remove their email address
    at any time from the app Settings / Profile screen.
  * Order Notifications: If customer email is null/empty, order confirmation,
    status updates, and delivery alerts automatically fall back to Twilio SMS.

2. CUSTOMER REGISTRATION API
--------------------------------------------------------------------------------
Endpoint: POST /mobileapi/customer/auth/register
Content-Type: application/json

Request Payload:
{
  "name": "Jane Doe",
  "phone": "9876543210",              // MANDATORY: digits or E.164
  "phoneCountryCode": "+91",          // OPTIONAL: defaults to system default (+91)
  "email": "jane@example.com",        // OPTIONAL: can be omitted, "", or null
  "password": "SecurePassword123!",   // MANDATORY
  "acceptTerms": true,                // MANDATORY
  "deviceId": "optional-uuid",        // OPTIONAL
  "platform": "android"               // OPTIONAL: "android" | "ios"
}

Behavior:
  * Validates phone number format and ensures phone is not already in use.
  * If email is provided, validates RFC email format and checks uniqueness.
  * Generates a 6-digit OTP and dispatches SMS via Twilio to the phone number.
  * If email was provided, also dispatches verification OTP to email.

Success Response (201 Created):
{
  "success": true,
  "message": "Registration successful. Please verify your mobile number.",
  "data": {
    "userId": "cuid_customer_12345",
    "email": "jane@example.com",     // or null if omitted
    "phone": "+919876543210",
    "isEmailVerified": false,
    "isPhoneVerified": false,
    "expiresIn": 600,                // OTP valid for 10 minutes (in seconds)
    "resendCooldown": 60,            // Resend button cooldown 60 seconds
    "verifyUrl": "/mobileapi/customer/auth/verify-otp?phone=%2B919876543210"
  }
}

Error Responses:
  * 400 Bad Request: { "success": false, "error": "Phone number is required" }
  * 400 Bad Request: { "success": false, "error": "Please enter a valid email address" }
  * 409 Conflict:    { "success": false, "error": "An account with this phone number already exists" }
  * 409 Conflict:    { "success": false, "error": "An account with this email already exists" }

3. OTP VERIFICATION APIS
--------------------------------------------------------------------------------
Primary Unified Endpoint: POST /mobileapi/customer/auth/verify-otp
Content-Type: application/json

Option A - Verify via Mobile Phone Number (Default / SMS OTP):
{
  "phone": "+919876543210",          // or "9876543210"
  "phoneCountryCode": "+91",
  "otp": "123456"
}

Option B - Verify via Email (if email was provided):
{
  "email": "jane@example.com",
  "otp": "123456"
}

Dedicated Channel Endpoints (Alternative):
  * Phone OTP: POST /mobileapi/customer/auth/phone-otp/verify-otp
    Body: { "phone": "+919876543210", "phoneCountryCode": "+91", "otp": "123456" }
  * Email OTP: POST /mobileapi/customer/auth/email-otp/verify-otp
    Body: { "email": "jane@example.com", "otp": "123456" }

Success Response (200 OK):
{
  "success": true,
  "message": "Mobile number verified successfully",
  "data": {
    "user": {
      "id": "cuid_customer_12345",
      "name": "Jane Doe",
      "email": "jane@example.com",
      "phone": "+919876543210",
      "phoneCountryCode": "+91",
      "role": "CUSTOMER",
      "isEmailVerified": true,
      "isPhoneVerified": true
    },
    "tokens": {
      "accessToken": "eyJhbGciOi...",
      "refreshToken": "eyJhbGciOi...",
      "expiresIn": 86400
    }
  }
}

5. DUAL CREDENTIAL LOGIN API (EMAIL OR PHONE)
--------------------------------------------------------------------------------
Endpoint: POST /mobileapi/customer/auth/login
Content-Type: application/json

The mobile login UI should feature a single field: "Email or Mobile Number".
You can submit via any of the following payload formats:

Format 1 - Unified "identifier" (RECOMMENDED FOR NEW APPS):
{
  "identifier": "+919876543210",     // or "jane@example.com" or "9876543210"
  "password": "SecurePassword123!",
  "phoneCountryCode": "+91",
  "deviceId": "optional-device-id",
  "platform": "android"
}

Format 2 - Explicit "phone":
{
  "phone": "9876543210",
  "phoneCountryCode": "+91",
  "password": "SecurePassword123!"
}

Format 3 - Explicit "email" (BACKWARD COMPATIBLE):
{
  "email": "jane@example.com",
  "password": "SecurePassword123!"
}

Success Response (200 OK):
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {
      "id": "cuid_customer_12345",
      "name": "Jane Doe",
      "email": null,                 // or "jane@example.com" if registered
      "phone": "+919876543210",
      "phoneCountryCode": "+91",
      "role": "CUSTOMER",
      "isEmailVerified": true
    },
    "tokens": {
      "accessToken": "eyJhbGciOi...",
      "refreshToken": "eyJhbGciOi...",
      "expiresIn": 2592000
    },
    "sessionInfo": {
      "expiresIn": 2592000,
      "tokenType": "Bearer"
    }
  }
}

Unverified Account Handling (403 Forbidden):
If the account has not yet verified their phone/email:
{
  "success": false,
  "error": "Please verify your account first",
  "needsVerification": true,
  "isVerified": false,
  "authStatus": "PENDING_VERIFICATION",
  "verifyUrl": "/mobileapi/customer/auth/verify-otp?phone=%2B919876543210",
  "data": {
    "email": null,
    "phone": "+919876543210"
  }
}
* Mobile Client Action: When response code is 403 and needsVerification is true (or isVerified is false),
  navigate directly to your OTP Verification Screen with the phone number pre-filled.

6. PASSWORDLESS OTP LOGIN (SMS OTP & EMAIL OTP)
--------------------------------------------------------------------------------
For apps that support passwordless instant login via OTP:

A. Phone Number OTP Login (SMS):
Step 1: Request Login OTP via SMS
Endpoint: POST /mobileapi/customer/auth/phone-otp/send-otp
Content-Type: application/json
Payload:
{
  "phone": "+919876543210",          // or "9876543210"
  "phoneCountryCode": "+91"
}
Response (200 OK):
{
  "success": true,
  "message": "Login OTP sent to mobile number",
  "data": { "phone": "+919876543210", "expiresIn": 600, "resendCooldown": 60 }
}

Step 2: Verify Login OTP
Endpoint: POST /mobileapi/customer/auth/phone-otp/verify-otp
Content-Type: application/json
Payload:
{
  "phone": "+919876543210",
  "otp": "123456"
}
Response (200 OK):
Returns { success: true, message: "OTP login successful", data: { user, tokens, sessionInfo } }
where tokens includes "phone: user.phone" claim.

B. Email Address OTP Login:
Step 1: Request Login OTP via Email
Endpoint: POST /mobileapi/customer/auth/email-otp/send-otp
Payload: { "email": "jane@example.com" }

Step 2: Verify Login OTP
Endpoint: POST /mobileapi/customer/auth/email-otp/verify-otp
Payload: { "email": "jane@example.com", "otp": "123456" }

7. SOCIAL LOGIN & PHONE BINDING (GOOGLE, APPLE, FACEBOOK)
--------------------------------------------------------------------------------
Endpoint: POST /mobileapi/customer/auth/social
Content-Type: application/json

Request Payload:
{
  "provider": "google",               // "google" | "apple" | "facebook"
  "idToken": "eyJhbGciOi...",         // OAuth ID token from SDK
  "accessToken": "ya29...",           // OAuth access token
  "name": "Jane Doe",                 // Profile name
  "email": "jane.oauth@gmail.com"     // Email provided by provider
}

Behavior & Phone Linking:
  * For social sign-ins, user account is created with verified email.
  * user.phone will be null initially for fresh social logins.
  * Generated JWT token payload includes "phone: null".
  * The mobile app can prompt the user to link their mobile phone number via
    PUT /mobileapi/customer/settings so they can receive SMS order updates.
  * Once linked, the user can also log in via their phone number.

9. AFTER-LOGIN: SETTINGS & PROFILE EMAIL MANAGEMENT
--------------------------------------------------------------------------------
Customers who signed up with only a phone number can add an email address
at any time from the app Settings / Edit Profile screen.

Endpoint: PUT /mobileapi/customer/settings  (or PATCH /mobileapi/customer/settings)
Headers:
  Authorization: Bearer <accessToken>
  Content-Type: application/json (or multipart/form-data)

Request Payload (JSON):
{
  "name": "Jane Doe",
  "email": "jane.doe@example.com",   // To set/update email
  "phone": "+919876543210"
}

To clear an email:
{
  "email": ""                        // Backend stores null in database
}

Backend Validation Rules:
  1. RFC Email Format: Validates email format if string is non-empty.
  2. Uniqueness Check: Checks if another user already has this email.
     If duplicate -> Returns 400: "This email address is already in use by another account"
  3. Safe Nullification: Empty string "" is saved as null to prevent database
     unique constraint collisions.

Success Response (200 OK):
{
  "success": true,
  "message": "Profile updated successfully",
  "data": {
    "id": "cuid_customer_12345",
    "name": "Jane Doe",
    "email": "jane.doe@example.com",
    "phone": "+919876543210"
  }
}

10. CHECKOUT, ORDER LIFECYCLE & SMS FALLBACK
--------------------------------------------------------------------------------
Endpoints:
  * Product Order:    POST /mobileapi/customer/checkout/place-order
  * Service Booking:  POST /mobileapi/customer/checkout/place-service-order
  * Food Order:       POST /mobileapi/customer/foods/orders
  * Hotel Booking:    POST /mobileapi/customer/hotels/rooms/[id]/book

Notification Dispatch Rules:
  * If customer has an email address -> System sends confirmation email.
  * If customer has NO email address -> System automatically sends Twilio SMS
    to customer's mobile number.
  * Mobile Client Requirement: Ensure shipping/contact phone number is always
    collected and validated on checkout screens.
